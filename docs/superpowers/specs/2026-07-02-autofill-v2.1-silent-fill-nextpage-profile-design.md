# Autofill v2.1: Silent fill, Next-page gate, richer profile

**Date:** 2026-07-02 · **Status:** User-directed (explicit requests, gates waived) · **Follows:** autofill v2 (@b096039)

## User requests (verbatim intent)

1. Remove the "Answers to review" Accept/Skip section — one Autofill click fills
   everything the AI answers, silently.
2. Multi-page apps: a **Next page** button at the bottom of the panel advances to
   the next page and the fill happens there automatically — never re-click
   Autofill. (Supersedes v2's fully-automatic advance: the human gate moves from
   per-answer to per-page.)
3. The profile must accept much more information — address, postal code, veteran
   status "and these types of questions" — because the AI cannot know them.

## A — Silent AI fill (remove the review gate)

- `planAiFill` ignores `needsReview`: every non-empty backend answer becomes a
  simple target. `AiFillPlan.drafts`, `AiDraft`, `StepTally.drafts`,
  `FlowProgress.drafts`, `FlowPauseReason "drafts"` are REMOVED.
- Overlay: `renderReviewSection`/`insertDraft`/`insertAllDrafts`/
  `maybeFlowResume`, the review host element, its CSS, and the "· N to review
  below" banner fragment are removed. `onFlowResume` leaves `OverlayCallbacks`/
  `FormOpName`/`ALL_OPS`/`VOID_OPS`.
- `FlowController`: `waitForDrafts`/`notifyDraftsCleared` removed.
- `onSaveAnswer` (user-confirmed memory save) is removed IF the review flow was
  its only caller (verify by grep); backend `SAVE_ANSWER` endpoint stays (unused
  by the overlay). Answers are NOT auto-saved to memory — an unreviewed AI answer
  must not poison cross-application memory. Backend `needsReview` computation is
  untouched (clients simply stop consuming it).
- EEO/sensitive gating unchanged (never AI-answered, never transmitted).

## B — Next-page gate

- `FlowController` per step: fill → pause checks → find advance button. Terminal
  → done (unchanged, never clicked). Advance found → emit new phase `"ready"`
  and WAIT for `notifyAdvanceRequested()` (or `stop()`). On request: re-run the
  blocked-condition wait once (captcha may have re-appeared), persist state,
  click, `waitForChange`, continue. `FlowPhase` += `"ready"`.
- Overlay: a `Next page →` button pinned at the BOTTOM of the panel, visible only
  in phase `"ready"` (flow line reads "Step N filled — review this page, then
  Next page"). Click → new void op `onFlowAdvance` (`FormOpName`/`ALL_OPS`/
  `VOID_OPS`/`OverlayCallbacks`) → `flowController?.notifyAdvanceRequested()`.
  Stop button unchanged.
- Navigation resume unchanged: the fresh page auto-fills (that is request #2's
  "it just does it"), then gates at `ready` again. Single-page forms: no button,
  flow finishes done. All guards (MAX_STEPS/TTL/loop/terminal) unchanged.

## C — Richer profile (address + EEO self-identification)

**Backend** (`UserSettings` columns, String default ""): `street_address`,
`address_state`, `postal_code`, `country` (city column exists), `eeo_gender`,
`eeo_race`, `eeo_hispanic`, `eeo_veteran`, `eeo_disability`. Migration follows
`backend/migrations/add_*.py` pattern. `profile.py` `ApplicationProfileOut/In` +
merge gain `addressStreet`, `addressCity` (maps `city`), `addressState`,
`postalCode`, `country`, and an `eeo` object `{gender, race, hispanicLatino,
veteranStatus, disabilityStatus}`; PATCH writes all of them; sync version bump
via the existing mechanism; `extension.py` sync exposes the same (it reuses the
merge — verify).

**Web app** (`frontend/src/pages/Settings.tsx`): an "Address" section (street /
city / province-state / postal code / country) and a "Self-identification
(optional)" section (gender, race/ethnicity, Hispanic/Latino, veteran status,
disability status — selects including "Prefer not to say") wired to the existing
profile PATCH. Copy makes clear self-identification is optional and only used
when the extension's "Fill EEO fields" setting is on.

**Extension**: `UserApplicationProfile` += the 5 address fields (eeo exists).
`FieldCategory` += `addressStreet | addressCity | addressState | postalCode |
country`. `AUTOCOMPLETE_MAP`: `address-line1→addressStreet`,
`address-level2→addressCity`, `address-level1→addressState`,
`postal-code→postalCode`, `country→country`, `country-name→country`. Keyword
patterns EN+FR (street/address/adresse; city/ville/town; state/province/région;
zip/postal; country/pays/nation). `resolveProfileValue` maps them
(addressCity falls back to `city ?? location`); `LOCAL_FAST_PATH` += all 5;
`CATEGORY_LABELS` entries. EEO resolution already exists behind `fillEEO` —
verify it reads `profile.eeo.*` and now receives real data. Country/state
dropdowns benefit from v2's option matching automatically.

## Out of scope

Auto-saving AI answers to memory; removing backend needsReview; address line 2;
date-available; any push/deploy (user's call).
