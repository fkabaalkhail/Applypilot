### Task B: Next-page gate

**Files:** content/flowController.ts, content/overlay.ts, content/contentScript.ts, content/crossFrame.ts, shared/types.ts; tests flowController.test.ts, overlayFlow.test.ts.

**Contract:**
- `FlowPhase` += `"ready"`. Controller: advance-kind button found → `this.emit("ready")` → `await waitForAdvanceRequest()` (promise; resolved by new `notifyAdvanceRequested()`, or `stop()` → stopped). After request: `if (!(await this.waitWhileBlocked())) return this.finishStopped();` then the existing persist→click→waitForChange sequence, unchanged.
- `FormOpName`/`ALL_OPS`/`VOID_OPS`/`OverlayCallbacks` += `onFlowAdvance` (void). contentScript: `onFlowAdvance: () => { flowController?.notifyAdvanceRequested(); }`.
- Overlay: `formatFlowProgress` gains `ready` → `` `Step ${p.step + 1} filled — review this page, then Next page` ``; a `Next page →` button (`#ap-flow-next`) pinned at the panel BOTTOM (a footer div appended as the LAST child of the panel container — find the panel root in showOverlay's markup; sticky/flex-end so it stays visible), shown only in phase `ready`, hidden on every other beat; click → `callbacks.onFlowAdvance()` and immediately hide the button (next beat re-shows if needed).
- Controller tests: replace auto-advance expectations — after observing a `"ready"` beat, tests call `controller.notifyAdvanceRequested()` (same microtask-spin pattern the drafts tests used); add: stop-during-ready → stopped; single-page (no advance) → done with no ready beat; terminal → done with no ready beat. overlayFlow test pins the new `ready` string.

Gates: full suite, tsc silent, build. Commit: `feat(autofill): user-gated Next page advance`

### Task C3: Extension address/postal/country categories

**Files:** shared/types.ts, shared/constants.ts, content/fieldMatcher.ts, content/aiFillPlanner.ts (LOCAL_FAST_PATH); tests: fieldMatcher.test.ts (append) or new addressFields.test.ts.

**Contract:**
- `UserApplicationProfile` += `addressStreet: string; addressCity: string; addressState: string; postalCode: string; country: string;` (all default "" server-side; extension treats missing as "" via existing normalization — check how sync profile is defaulted and follow it).
- `FieldCategory` += `"addressStreet" | "addressCity" | "addressState" | "postalCode" | "country"`; `CATEGORY_LABELS` += (Street address / City / Province or state / Postal code / Country).
- fieldMatcher: `AUTOCOMPLETE_MAP` += `"address-line1": "addressStreet", "street-address": "addressStreet", "address-level2": "addressCity", "address-level1": "addressState", "postal-code": "postalCode", "country": "country", "country-name": "country"`. Keyword rules (mirror existing pattern style/weights of e.g. phone/location): street/address line/adresse → addressStreet (exclude "email address"! require street|line|civic|adresse when "address" alone is ambiguous with email — study how existing rules disambiguate and write a negative test `email address` → email); city/ville/town → addressCity; state/province/région (not "statement") → addressState; zip|postal (code)? → postalCode; country|pays → country.
- `resolveProfileValue`: addressStreet→profile.addressStreet; addressCity→`profile.addressCity || profile.location`; addressState→profile.addressState; postalCode→profile.postalCode; country→profile.country. Empty string → null (follow the existing empty-handling convention). `LOCAL_FAST_PATH` += all 5. Verify eeo categories already resolve from `profile.eeo` under fillEEO (report the line; no change expected).
- Tests: classification EN+FR fixtures per category incl. the `email address`→email negative and a `postal code`/`code postal` case; resolver mapping incl. the city fallback; a scanPage fixture asserting a labeled postal-code input gets `proposedValue` from a profile with the new fields.

Gates: full suite, tsc, build. Commit: `feat(autofill): address/postal/country field categories`
